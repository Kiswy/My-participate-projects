======================================================================
一、可直接提供给 ChatGPT 的项目概述
======================================================================

这是一个正在开发的“多功能预约系统”Java Web 项目，面向普通用户（学生/教职工）和管理员。

当前项目不是 Spring Boot，也不是 Maven/Gradle 工程，而是使用 IntelliJ IDEA、Smart Tomcat、JSP、Servlet、JDBC、SQL Server 和 Vue 3 CDN 构建的传统 Java Web 项目。

系统计划实现以下功能：
- 用户注册、登录和角色区分。
- 普通用户查看预约项目、立即预约、查看自己的预约、取消预约。
- 管理员查看全部预约、刷新预约数据、新增项目、修改项目、删除或关闭项目。
- 后续由同一套 Java 后端同时服务 Web 前端和 Android 客户端。

截至 2026-06-09，项目的真实状态是：
- 登录和注册的基础后端链路已经实现，并且当天 Tomcat 访问日志显示注册、普通用户登录、管理员登录均出现成功重定向。
- 普通用户首页和管理员首页的页面布局、页签切换、列表展示已经完成。
- 首页中的预约项目、我的预约、预约总览和项目管理数据仍全部写死在 JSP 内的 Vue 数组中。
- “立即预约”“取消预约”“刷新”“新增项目”“删除项目”等按钮只有外观，没有事件处理和后端接口。
- ReservationServlet 目前是空类，预约业务后端基本未开始。
- 没有登录会话、Token、权限过滤器或管理员接口保护，直接访问 JSP 可以绕过登录和角色判断。
- 没有自动化测试、标准构建脚本、项目级 web.xml、数据库建表 SQL 文件或 JSON API。

综合判断：项目已经完成“页面原型 + 最基础账号数据库链路”，但尚未完成预约系统的核心业务闭环。

======================================================================
四、当前架构和实际数据流
======================================================================

1. 注册数据流

register.jsp
-> POST /register
-> RegisterServlet
-> UserDao.register(username, password, phone)
-> JDBC INSERT INTO users(username,password,phone)
-> 成功后重定向 index.jsp

该链路已经实现，2026-06-09 的访问日志中出现：
- POST /register，HTTP 302
- 随后 GET /index.jsp，HTTP 200

2. 登录数据流

index.jsp
-> POST /login
-> LoginServlet
-> UserDao.login(username, password)
-> JDBC 查询 users 表
-> 根据 user.role 判断跳转页面

当前角色规则：
- role 等于中文“管理员”时跳转 homepage_Max.jsp。
- 其他任何非空角色都跳转 homepage.jsp。

2026-06-09 的访问日志中出现：
- POST /login -> homepage_Max.jsp，表示管理员登录链路曾成功。
- POST /login -> homepage.jsp，表示普通用户登录链路曾成功。

3. 首页数据流

homepage.jsp 和 homepage_Max.jsp
-> JSP include 引入四个局部页面
-> Vue 3 在浏览器中读取 JSP 内写死的数组
-> v-for 渲染卡片或表格

当前首页不会请求 Java 后端，也不会查询 SQL Server。页面刷新后仍显示固定演示数据。

4. 预约数据流

目前不存在真实数据流。

ReservationServlet 只是：
public class ReservationServlet {
}

它没有继承 HttpServlet、没有 @WebServlet、没有 doGet/doPost，也没有调用 DAO。

======================================================================
五、各文件职责和完成情况
======================================================================

1. src/Main.java

状态：仅供手工测试，不属于正式 Web 请求流程。

作用：
- 创建 UserDao。
- 使用固定用户名、密码和手机号调用 register()。
- 在控制台输出结果。

问题：
- 每次运行都会尝试向数据库插入固定测试用户。
- 如果用户名有唯一约束，重复运行会失败并打印异常。
- 不应被当成正式后端入口；真正入口是 Tomcat 中的 Servlet。

2. src/entity/User.java

状态：基础实现完成。

字段：
- id
- username
- password
- phone
- createTime
- role

已有无参构造方法和完整 getter/setter。

不足：
- createTime 使用 String，而不是 LocalDateTime/Timestamp。
- 实体直接包含明文 password。
- 与已有规划文档建议的 password_hash、real_name、email、created_at 字段不一致。

3. src/util/DBUtil.java

状态：基础数据库连接已实现，并且从运行结果看当前环境可以使用。

作用：
- 加载 SQL Server JDBC 驱动。
- 连接 localhost\\SQL2022 下的 AppointmentSystem 数据库。

严重问题：
- 数据库管理员账号和真实口令硬编码在源码中。
- 使用 sa 高权限账号，不符合最小权限原则。
- trustServerCertificate=true 会跳过服务器证书校验。
- 没有配置文件、环境变量或连接池。

4. src/dao/UserDao.java

状态：登录和注册的最小 JDBC 操作已完成。

已实现：
- login(username, password)
- register(username, password, phone)
- 使用 PreparedStatement，能够避免最基础的 SQL 注入。
- 登录成功时把数据库结果转换为 User。

不足：
- 密码以明文条件查询和明文方式写入数据库。
- 没有用户名是否存在的显式检查。
- 没有参数验证。
- 使用 SELECT *。
- 资源手工关闭，异常发生在中途时可能无法释放连接。
- 异常只 e.printStackTrace()，调用方只能得到 null/false，无法区分错误原因。
- 没有连接池、事务、日志框架或 DAO 接口。

5. src/servlet/LoginServlet.java

状态：基础登录跳转已实现。

路由：POST /login

已实现：
- 接收 username 和 password。
- 调用 UserDao.login()。
- 根据角色跳转普通用户页或管理员页。
- 登录失败输出简单中文文本。

未实现或存在问题：
- 没有把 User 或 userId 写入 HttpSession。
- 没有 Token。
- 登录成功只重定向，后续请求不知道当前用户是谁。
- 没有输入验证、空值处理和统一错误页面。
- 没有设置 request 字符编码和 response 内容类型。
- 角色值使用中文“管理员”，与规划文档中的 ADMIN/USER 约定冲突。
- 未知角色会被默认当作普通用户。

6. src/servlet/RegisterServlet.java

路由：POST /register

已实现：
- 接收 username、password、phone。
- 调用 UserDao.register()。

未实现或存在问题：

- 没有手机号格式校验。
- 没有确认密码。
- 没有密码强度要求和密码哈希。
- 没有显式处理重复用户名。
- 没有设置默认角色，依赖数据库默认值。
- 没有设置字符编码和响应内容类型。

======================================================================
九、当前最重要的技术问题和风险
======================================================================

严重级别：高

1. 数据库真实口令硬编码在 DBUtil.java 中。
影响：源码泄露等同于数据库凭据泄露，而且使用的是 sa 高权限账号。

2. 用户密码明文存储和明文比较。
影响：数据库泄露后所有用户密码直接暴露。

3. 没有认证状态和服务端授权。
影响：任何人都可以直接访问普通首页或管理员首页；后续即使增加管理员按钮，也不能只靠页面隐藏保护。

4. 预约业务没有事务和并发控制。
影响：未来直接实现“先查剩余、再插入”时，多个请求可能同时通过检查，造成超额预约。

严重级别：中

5. 数据库字段约定不一致。
当前代码使用：password、create_time、中文“管理员”。
规划文档使用：password_hash、created_at、USER/ADMIN。
影响：继续开发前必须先确定唯一的数据字典，否则实体、SQL 和接口会持续冲突。

6. 注册和登录没有输入校验、字符编码设置和精确错误处理。
影响：空数据、非法手机号、重复用户名、中文参数和数据库故障都可能产生不清晰结果。

7. Vue 依赖公网 CDN。
影响：离线、校园网限制或 unpkg 不可用时，首页 Vue 渲染和页签逻辑会失效。

8. 没有标准依赖和构建管理。
影响：项目只能依赖当前 IDEA/Tomcat 本地配置，换电脑、部署服务器或团队协作时容易失败。

9. 页面资源和表单路径依赖根上下文。
影响：当前部署在 / 下可用，若改为 /appointmentSystem，/css、/images、/register 等路径可能错误。

10. DAO 资源管理不稳健。
影响：异常路径可能造成 JDBC 连接、PreparedStatement 或 ResultSet 未关闭。

严重级别：低或维护性问题

11. src/servlet 下存在 LoginServlet.class 编译文件。
影响：编译产物混入源码目录，可能造成旧类混淆，应由构建输出目录统一管理。

12. 演示数据日期不一致。
- 首页项目显示 4/10、4/11、4/12，没有年份。
- 管理员预约示例使用 2024-04-08。
- 当前日期为 2026-06-09。
影响：数据明显是静态样例，不能用于真实业务判断。

13. Main.java 会直接插入固定测试账号。
影响：误运行可能污染数据库或触发重复键异常。

十、现有规划文档与当前源码的差异
======================================================================

项目中已有“后端开发思路_SQLServer版.txt”。该文档提供了较完整的目标方案，但其中“后端还没有真正开始实现”的描述已经过时。

当前实际已经完成规划顺序中的：
- 配置 SQL Server JDBC 驱动。
- 编写 DBUtil。
- 编写 User 实体。
- 编写 UserDao 的注册和登录 SQL。
- 编写注册 Servlet。
- 编写登录 Servlet。

当前仍未完成规划顺序中的：
- Category、Project、Reservation 实体。
- ProjectDao、ReservationDao、CategoryDao。
- /api/projects。
- 立即预约接口。
- 我的预约接口。
- 取消预约接口。
- 管理员预约总览接口。
- 管理员项目管理接口。
- Web 从假数据切换到接口。
- Android 从假数据切换到接口。

需要先解决的规划冲突：
- 当前代码是表单提交 + JSP 重定向；规划目标是 /api + JSON。
- 当前字段名和角色值与规划文档不同。
- 当前项目没有 service 层、JSON 工具或 Token 工具。

建议选择一种清晰路线：

路线 A：先完成传统 JSP + Session 版本。
- 保留登录/注册表单。
- 使用 HttpSession 保存当前用户。
- Servlet 将数据放入 request/session，再由 JSP 渲染。
- 适合较小的课程项目，但不方便 Android 共用。

路线 B：按已有规划完成统一 JSON API（更符合项目长期目标）。
- Servlet 统一放在 /api 下。
- Web 使用 fetch 调 API。
- Android 调用同一套 API。
- 使用 Session 或 Token 完成认证。
- 更适合 Web + Android 共用后端。

如果 Android 共用后端是确定目标，应优先选择路线 B，避免先写一套 JSP 专用后端后再重构。
